<!-- locale:en -->

A while ago I wrote about field-testing my second brain against a real ticket. The honest grade was a B: useful, not decisive.

The most interesting thing that test produced wasn't the 92% context reduction. It was a complaint.

The agent kept retrieving **files** when what it needed was **paragraphs**.

Lorekeeper is the tool I'm building to fix that, and over the last few weeks it stopped being a folder convention and became an actual retrieval contract.

Most of the work wasn't ranking. It was deciding what a retrievable thing *is*.

## Folders are a viewer's problem

The first thing I threw out was numbered PARA folders.

Numeric prefixes exist to force sort order in a file browser. Encoding a viewer's concern as architecture is how a knowledge base becomes unmovable.

So the folders are thin and carry only an epistemic role: where a thing sits in the chain from raw artifact to synthesized knowledge:

```text
external artifact → sources/ → notes/ → entities/
```

And frontmatter is authoritative for everything that matters: type, status, provenance, links.

That single split is what lets me reorganize my vault on a Sunday afternoon without breaking retrieval.

One contract is frozen: provenance edges always point from the derived artifact to its origin. Inverse edges are never stored. Backlinks are computed, never written. A note that says where it came from stays true no matter what gets added later.

## A file is the wrong unit

The index doesn't address files. It addresses **spans**: a path, a heading anchor, and a 1-based line range.

A three-thousand-word note about deployment isn't one fact. It's forty. Retrieving the whole thing to answer one question is the same mistake as pasting a repository into a prompt. You get the answer, and thirty-nine irrelevant things competing with it for attention.

Ranking is BM25 over the span text plus a weighted metadata document. A prototype settled that early, and I deliberately stopped treating ranking as a Feature that needed inventing.

A question rarely arrives in the wording the note was written in. So a search takes several alternate phrasings in one call and fuses the ranked lists with Reciprocal Rank Fusion:

```bash
lore search ~/brain "retry policy" "backoff strategy" "what happens when a request fails"
```

Near-duplicate spans get suppressed, so a paragraph copy-pasted across nine files doesn't take nine slots in a list of five.

Every result carries path, anchor, line range, score and the span text itself. Five fields, because an agent weighing evidence needs the address, not just the claim.

## Two things it refuses to do

There is no relevance cutoff. Anywhere.

A low score never withholds a result, and no "nothing found" verdict is ever derived from a number. This matters more than it looks: **a retrieval score cannot prove that knowledge is absent.** It's a documented limitation, not a defect waiting for a fix, and the agent-facing instructions say so explicitly. The agent treats results as evidence, may search again, and may conclude the evidence is insufficient, which is a very different sentence from "there is nothing."

And correctness never depends on the metadata being good. A file with no frontmatter, or with frontmatter nobody recognizes, indexes as ordinary knowledge. Ranking reads neither `type` nor `about` as structure.

That's deliberate. The moment retrieval quality depends on perfect tagging, the system only works for the version of me that has time to tag perfectly.

Reading and indexing never write to your notes either. Indexing a vault leaves every file byte-identical.

## What it costs to ask

I'd rather measure than claim.

Over a deterministic synthetic corpus of 3,000 notes (10,537 spans, about 3.2 MB, with 907 paragraphs deliberately duplicated across files):

| Measure | Value |
| --- | --- |
| Walk, read and split | 81 ms |
| Build the index | 64 ms |
| Query, one wording | 2.3 ms |
| Query, three wordings fused and suppressed | 6.9 ms |
| `lore search` end to end, three wordings, `--json` | 129 ms |

Measured on an M5 with Node 26, query rows as medians of 20 runs.

The index is built in memory on every single command and never persisted. That looks wasteful until you read the table: persisting it would save roughly 150 ms and cost a managed file that can drift, go stale, and need invalidating.

At this size that trade is obviously bad. When the walk and index phases, the two that scale with the vault, start approaching the interactive reading, I'll revisit it. Not before.

There are no embeddings, no vectors, and no LLM call anywhere in the CLI. It runs offline with no credentials and no vendor. For a few thousand Markdown files, lexical retrieval isn't a compromise. It's the correct amount of machinery.

## The agent has to be told, and told correctly

None of this helps if a coding agent doesn't know the brain exists.

So initializing a brain generates an `AGENTS.md` at its root: a manifest-owned file stating what the brain is, the exact command including how to pass several wordings, the five result fields, and the absence limitation.

Regenerating it over a copy you've edited reports drift instead of overwriting. Your edits win.

The instruction to issue multiple wordings lives in that file deliberately. It isn't an optimization tip. It's part of the retrieval contract, because fusing three phrasings is what the ranking was designed around.

## And the number I didn't get to choose

The whole premise is that span retrieval is cheaper than reading notes. I measured that too, using the exact call the artifact teaches.

Five results, from five distinct files.

The whole notes those spans live in: **5,604 bytes.** The JSON payload the agent actually receives: **2,847 bytes.**

Roughly **2.0x**. Modest.

I'm reporting it as measured rather than as improved, and three things bound it. All three I could have tuned away and didn't.

The baseline is deliberately generous. It charges only for the files the returned spans came from, as if the agent had already known which five notes to open. Without span retrieval it wouldn't have known, so 2.0x is a floor, not a best case.

The synthetic notes average about a kilobyte, so a span can only be around 3.4 times smaller than the note holding it. A vault of longer notes would show a bigger saving. I didn't lengthen the corpus to produce one.

And the payload is pretty-printed, which is 12% of its bytes. Compact JSON would read 2.2x, but the output format is a contract other things depend on, and changing a contract to improve a benchmark is exactly the kind of thing this project exists to avoid.

Bytes are a labelled proxy for token cost, not a token count. Counting real tokens means shipping a tokenizer and picking a vendor, and the CLI makes zero LLM calls by design.

## The thing that made me laugh

`AGENTS.md`, the file that teaches an agent how to search, is itself indexed by the search.

On its own illustrative example query it outranks the note it was trying to demonstrate. 0.0492 against 0.0484.

I could exclude it by filename. That would mean retrieval deriving meaning from a path, which contradicts the entire folder decision above. I could exclude it by frontmatter, which needs vocabulary I've deliberately left unfrozen.

There is no small correct fix, so there isn't one. It's written down as a known behavior instead of quietly patched.

Across four realistic questions the intended note ranked first every time, with the artifact appearing only lower down at about a third of the winning score.

## Where this is going

Pathfinder finds the way. Lorekeeper remembers the journey.

The retrieval spine is the part I wanted to get right first, because everything later (capability sync, an MCP adapter, mobile capture) is a transport question over the same core.

I still don't need an AI that remembers everything.

I need the right seven paragraphs.

📜 **Plain Markdown. Your files. No vendor in the middle.**

Hace un tiempo escribí sobre poner a prueba mi segundo cerebro contra un ticket real. La nota honesta fue un notable: útil, no decisivo.

Lo más interesante que salió de esa prueba no fue el 92% de reducción de contexto. Fue una queja.

El agente recuperaba **ficheros** cuando lo que necesitaba eran **párrafos**.

Lorekeeper es la herramienta que estoy construyendo para arreglar eso, y en las últimas semanas ha dejado de ser una convención de carpetas para convertirse en un contrato de recuperación de verdad.

La mayor parte del trabajo no fue el ranking. Fue decidir qué *es* una cosa recuperable.

## Las carpetas son un problema del visor

Lo primero que descarté fueron las carpetas PARA numeradas.

Los prefijos numéricos existen para forzar el orden en un explorador de ficheros. Codificar la preocupación de un visor como arquitectura es la forma de convertir una base de conocimiento en algo inamovible.

Así que las carpetas son finas y solo llevan un rol epistémico: dónde está algo en la cadena que va del artefacto en bruto al conocimiento sintetizado:

```text
artefacto externo → sources/ → notes/ → entities/
```

Y el frontmatter es autoritativo para todo lo que importa: tipo, estado, procedencia, enlaces.

Esa única separación es lo que me permite reorganizar mi vault un domingo por la tarde sin romper la recuperación.

Hay un contrato congelado: las aristas de procedencia siempre apuntan del artefacto derivado a su origen. Las aristas inversas nunca se almacenan. Los backlinks se calculan, nunca se escriben. Una nota que dice de dónde viene sigue siendo cierta pase lo que pase después.

## Un fichero es la unidad equivocada

El índice no direcciona ficheros. Direcciona **fragmentos**: una ruta, un ancla de encabezado y un rango de líneas empezando en 1.

Una nota de tres mil palabras sobre despliegues no es un hecho. Son cuarenta. Recuperarla entera para responder a una pregunta es el mismo error que pegar un repositorio en un prompt. Obtienes la respuesta, y treinta y nueve cosas irrelevantes compitiendo con ella por la atención.

El ranking es BM25 sobre el texto del fragmento más un documento de metadatos ponderado. Un prototipo lo resolvió pronto, y dejé deliberadamente de tratar el ranking como una Feature que hubiera que inventar.

Una pregunta casi nunca llega con las palabras con las que se escribió la nota. Así que una búsqueda acepta varias formulaciones alternativas en una sola llamada y fusiona las listas ordenadas con Reciprocal Rank Fusion:

```bash
lore search ~/brain "política de reintentos" "estrategia de backoff" "qué pasa cuando falla una petición"
```

Los fragmentos casi duplicados se suprimen, así que un párrafo copiado en nueve ficheros no ocupa nueve huecos en una lista de cinco.

Cada resultado lleva ruta, ancla, rango de líneas, puntuación y el propio texto del fragmento. Cinco campos, porque un agente que evalúa evidencia necesita la dirección, no solo la afirmación.

## Dos cosas que se niega a hacer

No hay umbral de relevancia. En ninguna parte.

Una puntuación baja nunca retiene un resultado, y ningún veredicto de "no hay nada" se deriva jamás de un número. Esto importa más de lo que parece: **una puntuación de recuperación no puede demostrar que un conocimiento esté ausente.** Es una limitación documentada, no un defecto esperando arreglo, y las instrucciones para el agente lo dicen explícitamente. El agente trata los resultados como evidencia, puede volver a buscar, y puede concluir que la evidencia es insuficiente, que es una frase muy distinta de "no hay nada".

Y la corrección nunca depende de que los metadatos sean buenos. Un fichero sin frontmatter, o con frontmatter que nadie reconoce, se indexa como conocimiento ordinario. El ranking no lee ni `type` ni `about` como estructura.

Es deliberado. En el momento en que la calidad de la recuperación depende de un etiquetado perfecto, el sistema solo funciona para la versión de mí que tiene tiempo de etiquetar perfectamente.

Leer e indexar tampoco escriben nunca en tus notas. Indexar un vault deja cada fichero byte a byte idéntico.

## Lo que cuesta preguntar

Prefiero medir a afirmar.

Sobre un corpus sintético determinista de 3.000 notas (10.537 fragmentos, unos 3,2 MB, con 907 párrafos duplicados a propósito entre ficheros):

| Medida | Valor |
| --- | --- |
| Recorrer, leer y trocear | 81 ms |
| Construir el índice | 64 ms |
| Consulta, una formulación | 2,3 ms |
| Consulta, tres formulaciones fusionadas y suprimidas | 6,9 ms |
| `lore search` de punta a punta, tres formulaciones, `--json` | 129 ms |

Medido en un M5 con Node 26; las filas de consulta son medianas de 20 ejecuciones.

El índice se construye en memoria en cada comando y nunca se persiste. Parece un desperdicio hasta que lees la tabla: persistirlo ahorraría unos 150 ms y costaría un fichero gestionado que puede desviarse, quedarse obsoleto y necesitar invalidación.

A este tamaño ese intercambio es malo de forma evidente. Cuando las fases de recorrido e indexado, las dos que escalan con el vault, empiecen a acercarse a la lectura interactiva, lo revisaré. Antes no.

No hay embeddings, ni vectores, ni ninguna llamada a un LLM en la CLI. Funciona offline, sin credenciales y sin proveedor. Para unos pocos miles de ficheros Markdown, la recuperación léxica no es un compromiso. Es la cantidad correcta de maquinaria.

## Al agente hay que decírselo, y decírselo bien

Nada de esto sirve si un agente de código no sabe que el cerebro existe.

Así que inicializar un cerebro genera un `AGENTS.md` en su raíz: un fichero gestionado por el manifiesto que dice qué es el cerebro, el comando exacto incluyendo cómo pasar varias formulaciones, los cinco campos del resultado y la limitación sobre la ausencia.

Regenerarlo sobre una copia que hayas editado reporta desviación en vez de sobrescribir. Ganan tus ediciones.

La instrucción de emitir varias formulaciones vive en ese fichero deliberadamente. No es un consejo de optimización. Es parte del contrato de recuperación, porque fusionar tres formulaciones es aquello para lo que se diseñó el ranking.

## Y el número que no pude elegir

Toda la premisa es que recuperar fragmentos es más barato que leer notas. Eso también lo medí, usando la llamada exacta que enseña el artefacto.

Cinco resultados, de cinco ficheros distintos.

Las notas enteras donde viven esos fragmentos: **5.604 bytes.** El payload JSON que el agente recibe de verdad: **2.847 bytes.**

Aproximadamente **2,0x**. Modesto.

Lo reporto como medido, no como mejorado, y hay tres cosas que lo acotan. Las tres podría haberlas ajustado y no las ajusté.

La línea base es deliberadamente generosa. Solo cobra por los ficheros de los que salieron los fragmentos devueltos, como si el agente ya hubiera sabido qué cinco notas abrir. Sin recuperación por fragmentos no lo habría sabido, así que 2,0x es un suelo, no un mejor caso.

Las notas sintéticas rondan el kilobyte, así que un fragmento solo puede ser unas 3,4 veces más pequeño que la nota que lo contiene. Un vault de notas más largas mostraría un ahorro mayor. No alargué el corpus para conseguirlo.

Y el payload está formateado con indentación, que es el 12% de sus bytes. Con JSON compacto saldría 2,2x, pero el formato de salida es un contrato del que dependen otras cosas, y cambiar un contrato para mejorar un benchmark es exactamente el tipo de cosa que este proyecto existe para evitar.

Los bytes son un proxy etiquetado del coste en tokens, no un recuento de tokens. Contar tokens reales significa incluir un tokenizador y elegir un proveedor, y la CLI hace cero llamadas a LLM por diseño.

## Lo que me hizo reír

`AGENTS.md`, el fichero que enseña a un agente a buscar, está a su vez indexado por la búsqueda.

En su propia consulta de ejemplo, supera a la nota que intentaba demostrar. 0,0492 contra 0,0484.

Podría excluirlo por nombre de fichero. Eso significaría que la recuperación deriva significado de una ruta, lo cual contradice toda la decisión de carpetas de más arriba. Podría excluirlo por frontmatter, lo cual necesita vocabulario que he dejado deliberadamente sin congelar.

No hay un arreglo pequeño y correcto, así que no hay ninguno. Está escrito como comportamiento conocido en vez de parcheado en silencio.

En cuatro preguntas realistas la nota buscada quedó primera todas las veces, y el artefacto aparecía solo más abajo, a aproximadamente un tercio de la puntuación ganadora.

## Hacia dónde va esto

Pathfinder encuentra el camino. Lorekeeper recuerda el viaje.

La columna vertebral de la recuperación es la parte que quería acertar primero, porque todo lo posterior (sincronización de capacidades, un adaptador MCP, captura móvil) es una cuestión de transporte sobre el mismo núcleo.

Sigo sin necesitar una IA que lo recuerde todo.

Necesito los siete párrafos correctos.

Il y a quelque temps, j'ai écrit sur le test de mon second cerveau face à un vrai ticket. La note honnête était un B : utile, pas décisif.

Ce que ce test a produit de plus intéressant n'était pas les 92 % de réduction de contexte. C'était une plainte.

L'agent récupérait des **fichiers** alors qu'il lui fallait des **paragraphes**.

Lorekeeper est l'outil que je construis pour corriger ça, et ces dernières semaines il a cessé d'être une convention de dossiers pour devenir un véritable contrat de recherche.

L'essentiel du travail n'a pas été le classement. Ça a été de décider ce qu'*est* une chose récupérable.

## Les dossiers sont un problème de visionneuse

La première chose que j'ai jetée, ce sont les dossiers PARA numérotés.

Les préfixes numériques existent pour forcer l'ordre de tri dans un explorateur de fichiers. Encoder la préoccupation d'une visionneuse dans l'architecture, c'est ainsi qu'une base de connaissances devient impossible à déplacer.

Les dossiers sont donc minces et ne portent qu'un rôle épistémique : où se situe une chose dans la chaîne qui va de l'artefact brut à la connaissance synthétisée :

```text
artefact externe → sources/ → notes/ → entities/
```

Et le frontmatter fait autorité sur tout ce qui compte : type, statut, provenance, liens.

Cette seule séparation est ce qui me permet de réorganiser mon vault un dimanche après-midi sans casser la recherche.

Un contrat est gelé : les arêtes de provenance pointent toujours de l'artefact dérivé vers son origine. Les arêtes inverses ne sont jamais stockées. Les backlinks sont calculés, jamais écrits. Une note qui dit d'où elle vient reste vraie quoi qu'on ajoute ensuite.

## Un fichier est la mauvaise unité

L'index n'adresse pas des fichiers. Il adresse des **fragments** : un chemin, une ancre de titre et une plage de lignes commençant à 1.

Une note de trois mille mots sur le déploiement n'est pas un fait. C'en est quarante. La récupérer entièrement pour répondre à une question, c'est la même erreur que coller un dépôt dans un prompt. Vous obtenez la réponse, et trente-neuf choses hors sujet qui lui disputent l'attention.

Le classement est un BM25 sur le texte du fragment plus un document de métadonnées pondéré. Un prototype l'a tranché tôt, et j'ai délibérément cessé de traiter le classement comme une Feature à inventer.

Une question arrive rarement avec les mots dans lesquels la note a été écrite. Une recherche accepte donc plusieurs formulations alternatives en un seul appel et fusionne les listes classées avec la Reciprocal Rank Fusion :

```bash
lore search ~/brain "politique de réessai" "stratégie de backoff" "que se passe-t-il quand une requête échoue"
```

Les fragments quasi dupliqués sont supprimés, donc un paragraphe copié dans neuf fichiers ne prend pas neuf places dans une liste de cinq.

Chaque résultat porte le chemin, l'ancre, la plage de lignes, le score et le texte du fragment lui-même. Cinq champs, parce qu'un agent qui pèse des preuves a besoin de l'adresse, pas seulement de l'affirmation.

## Deux choses qu'il refuse de faire

Il n'y a aucun seuil de pertinence. Nulle part.

Un score faible ne retient jamais un résultat, et aucun verdict « rien trouvé » n'est jamais dérivé d'un nombre. Cela compte plus qu'il n'y paraît : **un score de recherche ne peut pas prouver qu'une connaissance est absente.** C'est une limitation documentée, pas un défaut en attente de correction, et les instructions destinées à l'agent le disent explicitement. L'agent traite les résultats comme des preuves, peut rechercher à nouveau, et peut conclure qu'elles sont insuffisantes, ce qui est une phrase très différente de « il n'y a rien ».

Et la justesse ne dépend jamais de la qualité des métadonnées. Un fichier sans frontmatter, ou avec un frontmatter que personne ne reconnaît, est indexé comme une connaissance ordinaire. Le classement ne lit ni `type` ni `about` comme une structure.

C'est délibéré. Dès l'instant où la qualité de la recherche dépend d'un étiquetage parfait, le système ne fonctionne que pour la version de moi qui a le temps d'étiqueter parfaitement.

Lire et indexer n'écrivent jamais dans vos notes non plus. Indexer un vault laisse chaque fichier identique octet pour octet.

## Ce que coûte une question

Je préfère mesurer qu'affirmer.

Sur un corpus synthétique déterministe de 3 000 notes (10 537 fragments, environ 3,2 Mo, avec 907 paragraphes délibérément dupliqués entre fichiers) :

| Mesure | Valeur |
| --- | --- |
| Parcourir, lire et découper | 81 ms |
| Construire l'index | 64 ms |
| Requête, une formulation | 2,3 ms |
| Requête, trois formulations fusionnées et dédupliquées | 6,9 ms |
| `lore search` de bout en bout, trois formulations, `--json` | 129 ms |

Mesuré sur un M5 avec Node 26 ; les lignes de requête sont des médianes sur 20 exécutions.

L'index est construit en mémoire à chaque commande et n'est jamais persisté. Cela paraît du gaspillage jusqu'à ce qu'on lise le tableau : le persister économiserait environ 150 ms et coûterait un fichier géré qui peut dériver, devenir obsolète et nécessiter une invalidation.

À cette taille, le compromis est manifestement mauvais. Quand les phases de parcours et d'indexation, les deux qui grandissent avec le vault, commenceront à s'approcher du seuil interactif, je le reverrai. Pas avant.

Il n'y a ni embeddings, ni vecteurs, ni le moindre appel LLM dans la CLI. Elle fonctionne hors ligne, sans identifiants et sans fournisseur. Pour quelques milliers de fichiers Markdown, la recherche lexicale n'est pas un compromis. C'est exactement la bonne quantité de machinerie.

## Il faut le dire à l'agent, et bien le dire

Rien de tout cela ne sert si un agent de code ignore que le cerveau existe.

Initialiser un cerveau génère donc un `AGENTS.md` à sa racine : un fichier détenu par le manifeste qui indique ce qu'est le cerveau, la commande exacte avec la façon de passer plusieurs formulations, les cinq champs du résultat et la limitation sur l'absence.

Le régénérer par-dessus une copie que vous avez modifiée signale une dérive au lieu d'écraser. Vos modifications gagnent.

L'instruction d'émettre plusieurs formulations vit dans ce fichier délibérément. Ce n'est pas un conseil d'optimisation. Cela fait partie du contrat de recherche, parce que fusionner trois formulations est précisément ce autour de quoi le classement a été conçu.

## Et le chiffre que je n'ai pas pu choisir

Toute la prémisse est que récupérer des fragments coûte moins cher que lire des notes. Je l'ai mesuré aussi, avec l'appel exact que l'artefact enseigne.

Cinq résultats, issus de cinq fichiers distincts.

Les notes entières où vivent ces fragments : **5 604 octets.** La charge utile JSON que l'agent reçoit réellement : **2 847 octets.**

Environ **2,0x**. Modeste.

Je le rapporte tel que mesuré, pas tel qu'amélioré, et trois choses le bornent. J'aurais pu les ajuster toutes les trois et je ne l'ai pas fait.

La ligne de base est délibérément généreuse. Elle ne facture que les fichiers d'où proviennent les fragments renvoyés, comme si l'agent avait déjà su quelles cinq notes ouvrir. Sans recherche par fragments, il ne l'aurait pas su : 2,0x est donc un plancher, pas un meilleur cas.

Les notes synthétiques font environ un kilo-octet, donc un fragment ne peut être qu'environ 3,4 fois plus petit que la note qui le contient. Un vault de notes plus longues montrerait une économie supérieure. Je n'ai pas allongé le corpus pour en obtenir une.

Et la charge utile est indentée, ce qui représente 12 % de ses octets. En JSON compact, elle afficherait 2,2x, mais le format de sortie est un contrat dont d'autres choses dépendent, et modifier un contrat pour améliorer un benchmark est exactement le genre de chose que ce projet existe pour éviter.

Les octets sont un proxy assumé du coût en tokens, pas un comptage de tokens. Compter de vrais tokens implique d'embarquer un tokenizer et de choisir un fournisseur, et la CLI ne fait aucun appel LLM par conception.

## Ce qui m'a fait rire

`AGENTS.md`, le fichier qui apprend à un agent à chercher, est lui-même indexé par la recherche.

Sur sa propre requête d'exemple, il devance la note qu'il essayait de démontrer. 0,0492 contre 0,0484.

Je pourrais l'exclure par son nom de fichier. Cela reviendrait à faire dériver du sens d'un chemin, ce qui contredit toute la décision sur les dossiers plus haut. Je pourrais l'exclure par frontmatter, ce qui exige un vocabulaire que j'ai délibérément laissé non gelé.

Il n'existe pas de petite correction juste, donc il n'y en a aucune. C'est consigné comme un comportement connu plutôt que rustiné en silence.

Sur quatre questions réalistes, la note visée est arrivée première à chaque fois, l'artefact n'apparaissant que plus bas, à environ un tiers du score gagnant.

## Où cela va
