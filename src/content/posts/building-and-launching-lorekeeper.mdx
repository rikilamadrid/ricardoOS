I have said "I already wrote this down somewhere" more times than I'd like to admit.

The frustrating part is that it's usually true. The note exists. It's in a Markdown file I wrote months ago, under a heading I don't remember, in a file I wouldn't think to open. The knowledge is there. It's just not *recoverable*, and knowledge you can't recover is about as useful as knowledge you never had.

Lorekeeper started as my answer to that sentence. This week it became a real thing: a package on npm, a documentation site, its own identity, a release pipeline, and a seat in the Wonder Wagon family of tools I've been building.

This isn't a changelog. It's what it took to get a small tool from "works on my machine" to "a stranger can install it", and the handful of decisions I'd make again.

## The product in one sentence

The tagline changed late. The earlier version ended with "…You cannot find it again." Accurate, and a little bleak. The one I approved is this:

**You already wrote it down. Find the passage that answers.**

The important word is *passage*.

Lorekeeper is a CLI with three commands. `lore init` creates a brain, which is just a directory of Markdown, or adopts a vault you already have without rewriting a single file. `lore capture` files a thought or a URL. `lore search` ranks the passages of that brain against a question.

Trying it takes one line:

```sh
npx create-lorekeeper@0.1.0 init ~/brain
```

That gives you five folders (`inbox/`, `daily/`, `notes/`, `sources/`, `entities/`), seven starter files, an `AGENTS.md` that tells a coding agent the directory is searchable, and a manifest at `.lorekeeper/manifest.json` recording which files the toolkit wrote. Everything else in that directory is yours, and `lore` won't touch it.

It runs offline. No account, no API key, no network call, no language model. It needs Node 24 or newer, on macOS or Linux. Windows is out of scope for v0.1, and CI says so in a comment next to the matrix.

## Decision 1: the passage, not the file, is the unit

I wrote a whole post on [why Lorekeeper retrieves spans](/writing/lorekeeper-retrieves-spans), so here's the short version.

A three-thousand-word note about deployments isn't one fact. It's forty. If search returns the file, you get the answer plus thirty-nine things competing with it for attention. That's bad for me reading it, and worse for an agent paying for every byte of context.

So every result is an address: a path, the heading it sits under, a line range, a score, and the text. Here's a real run against a small note I wrote for this post, asking the same question two ways in one call:

```sh
$ npx create-lorekeeper@0.1.0 search ~/brain \
    "retry policy" "what happens when the upload fails" --limit 2
notes/deploy-retries.md#When the upload fails:12-13  score 0.0164
~/brain/notes/deploy-retries.md
    The FTP step retries three times with a thirty-second backoff, then gives up.
    If it gives up, re-run the workflow; it only uploads changed files.

notes/README.md#notes:3-8  score 0.0161
~/brain/notes/README.md
    What you have worked out, written in your own words.
    ...
```

Two lines of a file, not the file. The note never says "retry policy". The second wording found it, and fusion put it first.

Look at the second result too, because it's the honest part.

## Why I refused to fake certainty

That second hit is the `notes/` folder's README. It has nothing to do with retries. It scored 0.0161 against the right answer's 0.0164.

Those numbers aren't confidence. With several wordings, Lorekeeper fuses ranked lists with Reciprocal Rank Fusion, and 0.0164 is 1/61: the fused score for ranking first. It tells you where a passage placed, not whether it's correct.

This is the part of retrieval that's easy to lie about. **A ranking score cannot prove that something is absent.** During evaluation, a control question with no answer anywhere in the corpus outranked genuine questions that did have one. The top result can simply be the best of a bad field.

So Lorekeeper has no relevance threshold. Anywhere. A threshold would feel responsible, and it would turn an honest miss into a confident "nothing found". Instead, the `AGENTS.md` it writes tells the calling agent to treat results as evidence, search again in other words when the evidence doesn't settle the question, and say "the evidence is insufficient" rather than "your notes don't cover this".

The retrieval itself is deterministic lexical ranking. The intelligence is whatever agent you were already using. I'd rather ship a tool that is exactly as smart as it is than one that sounds smarter.

## Giving it a face

Lorekeeper is one of four tools in a family I call Wonder Wagon, alongside Pathfinder, Forge and Lama. `lore --help` puts the relationship in one line: "Pathfinder finds the way; Lorekeeper remembers the journey." In the family brief, Lorekeeper's interface is a reading room, deliberately the quietest of the four.

The mark is a four-point star held in a ring: what was found, and what keeps it. The four-point sparkle is the current AI cliché, so it never floats free. It's always enclosed. No brain, no node graph, no glow.

A few things didn't survive contact with reality. An earlier straight-sided star resolved into a cross at 16 pixels, so the flanks got curved. A brass that measured 2.70:1 against its background was changed, not shipped with a footnote. Review caught the wordmark being clipped by its own viewBox, about two units of the final R's leg sliced flat, before any favicon was rendered from it.

![The Lorekeeper documentation site in day mode, headline reading "You already wrote it down. Find the passage that answers."](/writing/building-and-launching-lorekeeper/home-day.png)

Day and night each get their own palette, and both are measured. The README ships a day and a night header in a `<picture>`, so GitHub dark mode gets the night one and npm falls back to day. At a colour terminal, `lore --help` paints the word `Lorekeeper` in periwinkle `#99A2F0` and closes with a dimmed serial, `LK-047`. Pathfinder is `PF-047`, Forge is `FG-047`. Piped output, `NO_COLOR`, `TERM=dumb` and `--json` carry no escape codes at all.

![The same page at night.](/writing/building-and-launching-lorekeeper/home-night.png)

I didn't use the terminal adapter's default signal colour, a gilt `#E2B45C`. At 16 colours it degrades to yellow, which is the family's `warn` severity and Forge's floor. The periwinkle degrades to bright blue, which means nothing else. That's the kind of decision that only shows up when you test the ugly terminals too.

## Decision 2: brand consistency as a failing test

Here's a problem I didn't expect from a brand exercise. The colours live in two repositories.

Lorekeeper's `brand/tokens/tokens.json` is the source. The Wonder Wagon UI library has its own `lorekeeper` theme that restates nine of those values, across day and night. When I promoted that theme from `draft` to `pilot`, the night accent changed from `#5D64C3` to `#99A2F0` with dark ink `#141521`, at 7.58:1.

Copied values drift. So both sides check the same nine-value map.

On the Lorekeeper side, `brand/terminal/build.mjs --check` used to compare only one value, `link`. It now compares all nine. On the Wonder Wagon side, `proof/lorekeeper.ts` checks the same nine against a pinned Lorekeeper fixture, with a test that is meant to fail on drift. Run against the old Wonder Wagon pin, the extended Lorekeeper check fails on `accent.night` and `accentInk.night`. Correctly. That was the promotion showing up as a red build until the pin moved.

The docs site has the same problem with a twist. Vercel has no sibling checkout of the UI library, so the theme arrives as a generated file, and `theme:check` fails if it's stale.

Between those, measured contrast (`brand:check`, 52 pairs), and byte-for-byte checks on the README images and terminal recording, "on brand" stopped being an opinion someone has in review. It's a CI step.

## Decision 3: one public package, private core

The monorepo has two packages. `@lorekeeper/core` does the real work and is private. The CLI imports it by name.

That import can't survive publication. If the published CLI says `import ... from '@lorekeeper/core'`, npm goes looking for a package that doesn't exist and the install dies with a 404 before `lore` prints its help.

I could have published core as a second public package. I'd decided early that core stays private, and I wanted that decision to hold. So the build takes the exact `tsc` output the tests saw and inlines core into one file, `dist/lore.js`, with esbuild. Then it checks its own output. The bundle may import only `node:*` built-ins and `yaml`, the one runtime dependency, and core must actually be inside it. Either failure stops the build.

A package check runs on every PR. It packs the tarball, inspects it, installs it into a fresh prefix, and runs the installed `lore` through `--version`, `--help`, `init` and `search --json`. Sixteen checks. The result is `create-lorekeeper-0.1.0.tgz`: four files, 20,402 bytes packed.

The build is deterministic, so the tarball has a fingerprint. The sha1 recorded when I approved the packaging, `3ef401e3…`, is the same one the registry serves today.

About the name. `lorekeeper` on npm belongs to an unrelated project, so the package is `create-lorekeeper` and the command it installs is `lore`. Not ideal. It also means `npx create-lorekeeper` reads naturally, which I'll take.

## Decision 4: release evidence describes what happened

This is the one I care most about, and it's mostly about copy.

Before the release, the README said Lorekeeper wasn't on a registry and installed from source. That was true. It would become false on release day, and the tempting move is to "fix" it early so everything looks ready. I didn't. The PR that built the README listed that line as deliberately deferred, along with a terminal screenshot that still read `Lorekeeper 0.0.0`. Both changed in the release PR itself, the one that set the version, with the screenshot re-recorded from the bundled binary. The docs site, which is where people actually land, waited longer. Its PR merged after the package was on the registry, and its description opens with a section titled "Publication is proven".

The docs site enforces the same idea mechanically. Every command output on it, including `lore --help` and `--version`, is generated from the built binary at build time. And a Vercel build refuses to deploy if that binary reports `0.0.0`. The site can't claim a release the binary doesn't have.

![The live CLI reference page, showing real lore --help output reading Lorekeeper 0.1.0.](/writing/building-and-launching-lorekeeper/cli-night.png)

The release process follows the same rule. The version comes from one place, the newest heading in `CHANGELOG.md`. The manifest, the Git tag and the GitHub Release must agree with it, and the workflow refuses otherwise.

npm can only bind a trusted publisher to a package that already exists, so `0.1.0` was published once by hand, from the verified tarball. Future releases go through `release.yml`, which is built to publish through npm trusted publishing with provenance, read the version back from the registry, and only then push the tag and create the Release. Every step skips an effect that already exists, so a failed run gets re-dispatched, never "fixed" with a new version number.

That design got tested sooner than I planned.

The first release dispatch failed. The workflow installs `npm@latest`, which was npm 12.1.0, and npm 12 prints `npm pack --json` as an object keyed by package name instead of an array. My verification script expected the array. Nothing was published, tagged or released by that run, because the checks come first. The fix taught the script both shapes. Under npm 12 the tarball's sha1 was byte-identical to the one already on the registry, which is exactly what you want to know before you tag it.

Re-dispatched, the run saw `create-lorekeeper@0.1.0 is already on the registry; publish will be skipped`, confirmed the registry served it, tagged `v0.1.0`, and created the Release.

For the record, CI runs every pull request on both macOS and Linux.

## The site

The documentation lives at [lorekeeper-bay.vercel.app](https://lorekeeper-bay.vercel.app). It's plain static Astro. No docs theme, no React. Twelve content pages in one reading column with a plain index beside it, which is what "reading room" turned out to mean in practice.

It also works offline. A service worker, generated from the site's own page list, saves every page and its assets on the first visit. After that, the pages open with no connection. Online, it goes to the network first, so you never read a stale page while connected. It requests nothing but the site's own files. A documentation site for an offline tool that stops working on a plane felt like a small betrayal.

## What I learned

Getting `lore search` to rank the right passage was the part I expected to be hard. Most of the pull requests after it worked were about something else, making every public statement about it true: the colour on the README, the version on the help screen, the install line on the site, the tag on the commit.

What worked was turning each of those claims into something a machine checks. Contrast pairs get measured. Theme values get compared across repositories. Doc specimens get generated from the binary. The tarball gets a fingerprint. The release copy waits for the registry.

None of that is glamorous. But when the release broke on a JSON shape I never touched, nothing half-shipped. It just stopped, and told me why.

Lorekeeper does one small thing: it finds the passage you already wrote. Taking it all the way from idea to identity to a package a stranger can install taught me more than the ranking did, and I'm keeping the checks for the next tool.

```sh
npx create-lorekeeper@0.1.0 init ~/brain
```

The code is on [GitHub](https://github.com/rikilamadrid/lorekeeper). If it finds something you forgot you wrote, I'd like to hear about it.

## El producto en una frase

El eslogan cambió tarde. La versión anterior terminaba con "…No puedes volver a encontrarlo." Exacto, y un poco sombrío. El que aprobé es este:

**You already wrote it down. Find the passage that answers.** Ya lo escribiste. Encuentra el pasaje que responde.

La palabra importante es *pasaje*.

Lorekeeper es una CLI con tres comandos. `lore init` crea un cerebro, que no es más que un directorio de Markdown, o adopta una bóveda que ya tienes sin reescribir ni un solo fichero. `lore capture` archiva una idea o una URL. `lore search` ordena los pasajes de ese cerebro frente a una pregunta.

Probarlo cuesta una línea:

```sh
npx create-lorekeeper@0.1.0 init ~/brain
```

Eso te da cinco carpetas (`inbox/`, `daily/`, `notes/`, `sources/`, `entities/`), siete ficheros iniciales, un `AGENTS.md` que le dice a un agente de código que el directorio se puede buscar, y un manifiesto en `.lorekeeper/manifest.json` que registra qué ficheros escribió la herramienta. Todo lo demás en ese directorio es tuyo, y `lore` no lo toca.

Funciona sin conexión. Sin cuenta, sin API key, sin llamadas de red, sin modelo de lenguaje. Necesita Node 24 o superior, en macOS o Linux. Windows queda fuera de la v0.1, y la CI lo dice en un comentario junto a la matriz.

## Decisión 1: la unidad es el pasaje, no el fichero

Ya escribí un post entero sobre [por qué Lorekeeper recupera fragmentos](/writing/lorekeeper-retrieves-spans), así que aquí va la versión corta.

Una nota de tres mil palabras sobre despliegues no es un dato. Son cuarenta. Si la búsqueda devuelve el fichero, recibes la respuesta más treinta y nueve cosas compitiendo con ella por la atención. Eso es malo para mí cuando lo leo, y peor para un agente que paga cada byte de contexto.

Así que cada resultado es una dirección: una ruta, el encabezado bajo el que está, un rango de líneas, una puntuación y el texto. Aquí tienes una ejecución real contra una nota pequeña que escribí para este post, haciendo la misma pregunta de dos formas en una sola llamada:

```sh
$ npx create-lorekeeper@0.1.0 search ~/brain \
    "retry policy" "what happens when the upload fails" --limit 2
notes/deploy-retries.md#When the upload fails:12-13  score 0.0164
~/brain/notes/deploy-retries.md
    The FTP step retries three times with a thirty-second backoff, then gives up.
    If it gives up, re-run the workflow; it only uploads changed files.

notes/README.md#notes:3-8  score 0.0161
~/brain/notes/README.md
    What you have worked out, written in your own words.
    ...
```

Dos líneas de un fichero, no el fichero. La nota nunca dice "retry policy". La segunda formulación la encontró, y la fusión la puso primera.

Mira también el segundo resultado, porque es la parte honesta.

## Por qué me negué a fingir certeza

Ese segundo resultado es el README de la carpeta `notes/`. No tiene nada que ver con reintentos. Sacó 0,0161 frente al 0,0164 de la respuesta correcta.

Esos números no son confianza. Con varias formulaciones, Lorekeeper fusiona listas ordenadas con Reciprocal Rank Fusion, y 0,0164 es 1/61: la puntuación fusionada de quedar primero. Te dice en qué posición quedó un pasaje, no si es correcto.

Esta es la parte de la recuperación en la que es fácil mentir. **Una puntuación de ranking no puede demostrar que algo no está.** Durante la evaluación, una pregunta de control sin respuesta en ningún lugar del corpus quedó por encima de preguntas reales que sí la tenían. El primer resultado puede ser simplemente el mejor de un mal grupo.

Por eso Lorekeeper no tiene umbral de relevancia. En ningún sitio. Un umbral parecería responsable, y convertiría un fallo honesto en un "no se encontró nada" muy seguro de sí mismo. En su lugar, el `AGENTS.md` que escribe le dice al agente que trate los resultados como evidencia, que vuelva a buscar con otras palabras si la evidencia no resuelve la pregunta, y que diga "la evidencia es insuficiente" en vez de "tus notas no cubren esto".

La recuperación en sí es un ranking léxico determinista. La inteligencia es el agente que ya estabas usando. Prefiero publicar una herramienta exactamente tan lista como es que una que suena más lista.

## Decisión 2: la coherencia de marca como un test que falla

Este es un problema que no esperaba de un ejercicio de marca. Los colores viven en dos repositorios.

El `brand/tokens/tokens.json` de Lorekeeper es la fuente. La librería de UI de Wonder Wagon tiene su propio tema `lorekeeper` que repite nueve de esos valores, entre día y noche. Cuando promoví ese tema de `draft` a `pilot`, el acento nocturno pasó de `#5D64C3` a `#99A2F0` con tinta oscura `#141521`, a 7,58:1.

Los valores copiados se desvían. Así que los dos lados comprueban el mismo mapa de nueve valores.

En el lado de Lorekeeper, `brand/terminal/build.mjs --check` antes comparaba un solo valor, `link`. Ahora compara los nueve. En el lado de Wonder Wagon, `proof/lorekeeper.ts` comprueba los mismos nueve contra un fixture fijado de Lorekeeper, con un test pensado para fallar si hay deriva. Ejecutado contra el pin antiguo de Wonder Wagon, el check ampliado de Lorekeeper falla en `accent.night` y `accentInk.night`. Correctamente. Era la promoción apareciendo como una build en rojo hasta que se movió el pin.

El sitio de documentación tiene el mismo problema con un giro. Vercel no tiene una copia hermana de la librería de UI, así que el tema llega como un fichero generado, y `theme:check` falla si está desactualizado.

Entre eso, el contraste medido (`brand:check`, 52 pares) y las comprobaciones byte a byte de las imágenes del README y la grabación del terminal, "estar en marca" dejó de ser una opinión en una revisión. Es un paso de CI.

## Decisión 3: un paquete público, un núcleo privado

El monorepo tiene dos paquetes. `@lorekeeper/core` hace el trabajo de verdad y es privado. La CLI lo importa por nombre.

Ese import no sobrevive a la publicación. Si la CLI publicada dice `import ... from '@lorekeeper/core'`, npm busca un paquete que no existe y la instalación muere con un 404 antes de que `lore` imprima su ayuda.

Podría haber publicado el núcleo como un segundo paquete público. Había decidido pronto que el núcleo se queda privado, y quería que esa decisión se mantuviera. Así que la build toma exactamente la salida de `tsc` que vieron los tests e integra el núcleo en un único fichero, `dist/lore.js`, con esbuild. Luego comprueba su propia salida. El bundle solo puede importar módulos `node:*` y `yaml`, la única dependencia en tiempo de ejecución, y el núcleo tiene que estar realmente dentro. Cualquiera de los dos fallos detiene la build.

En cada PR se ejecuta una verificación del paquete. Empaqueta el tarball, lo inspecciona, lo instala en un prefijo limpio y ejecuta el `lore` instalado con `--version`, `--help`, `init` y `search --json`. Dieciséis comprobaciones. El resultado es `create-lorekeeper-0.1.0.tgz`: cuatro ficheros, 20.402 bytes empaquetado.

La build es determinista, así que el tarball tiene una huella. El sha1 registrado cuando aprobé el empaquetado, `3ef401e3…`, es el mismo que sirve hoy el registro.

Sobre el nombre. `lorekeeper` en npm pertenece a un proyecto que no tiene nada que ver, así que el paquete es `create-lorekeeper` y el comando que instala es `lore`. No es lo ideal. También hace que `npx create-lorekeeper` se lea con naturalidad, y eso me lo quedo.

## Decisión 4: la evidencia de una release describe lo que pasó

Esta es la que más me importa, y va sobre todo de textos.

Antes de la release, el README decía que Lorekeeper no estaba en ningún registro y se instalaba desde el código fuente. Era verdad. Iba a dejar de serlo el día de la release, y lo tentador es "arreglarlo" antes para que todo parezca listo. No lo hice. El PR que construyó el README dejó esa línea aplazada a propósito, junto con una captura del terminal que todavía decía `Lorekeeper 0.0.0`. Las dos cambiaron en el propio PR de la release, el que fijó la versión, con la captura regrabada desde el binario empaquetado. El sitio de documentación, que es donde la gente llega de verdad, esperó más. Su PR se fusionó cuando el paquete ya estaba en el registro, y su descripción empieza con una sección titulada "Publication is proven".

El sitio de documentación aplica la misma idea de forma mecánica. Cada salida de comando que aparece en él, incluidos `lore --help` y `--version`, se genera desde el binario construido en tiempo de build. Y una build de Vercel se niega a desplegar si ese binario dice `0.0.0`. El sitio no puede anunciar una release que el binario no tiene.

![La página de referencia de la CLI en producción, con la salida real de lore --help que dice Lorekeeper 0.1.0.](/writing/building-and-launching-lorekeeper/cli-night.png)

El proceso de release sigue la misma regla. La versión sale de un único sitio, el encabezado más reciente de `CHANGELOG.md`. El manifiesto, el tag de Git y la GitHub Release tienen que coincidir con él, y el workflow se niega a ejecutarse si no.

npm solo puede vincular un trusted publisher a un paquete que ya existe, así que `0.1.0` se publicó una vez a mano, desde el tarball verificado. Las próximas releases pasan por `release.yml`, que está hecho para publicar mediante trusted publishing de npm con provenance, leer la versión de vuelta desde el registro y solo entonces subir el tag y crear la Release. Cada paso se salta un efecto que ya existe, así que una ejecución fallida se vuelve a lanzar, nunca se "arregla" con un número de versión nuevo.

Ese diseño se puso a prueba antes de lo previsto.

El primer lanzamiento de la release falló. El workflow instala `npm@latest`, que era npm 12.1.0, y npm 12 imprime `npm pack --json` como un objeto indexado por nombre de paquete en lugar de un array. Mi script de verificación esperaba el array. Esa ejecución no publicó, etiquetó ni creó nada, porque las comprobaciones van primero. El arreglo le enseñó al script las dos formas. Con npm 12, el sha1 del tarball era idéntico byte a byte al que ya estaba en el registro, que es justo lo que quieres saber antes de etiquetarlo.

Relanzada, la ejecución vio `create-lorekeeper@0.1.0 is already on the registry; publish will be skipped`, confirmó que el registro lo servía, etiquetó `v0.1.0` y creó la Release.

Para que conste, la CI ejecuta cada pull request en macOS y en Linux.

## El sitio

La documentación está en [lorekeeper-bay.vercel.app](https://lorekeeper-bay.vercel.app). Es Astro estático, sin más. Sin tema de documentación, sin React. Doce páginas de contenido en una sola columna de lectura con un índice sencillo al lado, que es lo que "sala de lectura" acabó significando en la práctica.

También funciona sin conexión. Un service worker, generado a partir de la propia lista de páginas del sitio, guarda cada página y sus recursos en la primera visita. A partir de ahí, las páginas se abren sin conexión. Con conexión, va primero a la red, así que nunca lees una página desactualizada mientras estás online. No pide nada que no sean los ficheros del propio sitio. Un sitio de documentación de una herramienta offline que deja de funcionar en un avión me parecía una pequeña traición.

## Lo que aprendí

Conseguir que `lore search` ordenara bien el pasaje correcto era la parte que esperaba que fuera difícil. La mayoría de los pull requests que vinieron después trataban de otra cosa, de hacer verdad cada afirmación pública sobre la herramienta: el color del README, la versión en la pantalla de ayuda, la línea de instalación en el sitio, el tag en el commit.

Lo que funcionó fue convertir cada una de esas afirmaciones en algo que comprueba una máquina. Los pares de contraste se miden. Los valores del tema se comparan entre repositorios. Los ejemplos de la documentación se generan desde el binario. El tarball tiene una huella. El texto de la release espera al registro.

Nada de eso es glamuroso. Pero cuando la release se rompió por la forma de un JSON que yo nunca toqué, nada quedó publicado a medias. Simplemente se paró y me dijo por qué.

Lorekeeper hace una cosa pequeña: encuentra el pasaje que ya escribiste. Llevarlo desde la idea hasta la identidad y hasta un paquete que un desconocido puede instalar me enseñó más que el ranking, y me quedo con las comprobaciones para la próxima herramienta.

```sh
npx create-lorekeeper@0.1.0 init ~/brain
```

El código está en [GitHub](https://github.com/rikilamadrid/lorekeeper). Si encuentra algo que habías olvidado que escribiste, me gustaría saberlo.

J'ai dit "je l'ai déjà noté quelque part" plus souvent que je ne voudrais l'admettre.

Le plus frustrant, c'est que c'est généralement vrai. La note existe. Elle est dans un fichier Markdown écrit il y a des mois, sous un titre dont je ne me souviens pas, dans un fichier que je n'aurais pas l'idée d'ouvrir. Le savoir est là. Il n'est simplement pas *récupérable*, et un savoir qu'on ne peut pas récupérer vaut à peu près autant qu'un savoir qu'on n'a jamais eu.

Lorekeeper est né comme ma réponse à cette phrase. Cette semaine, c'est devenu quelque chose de réel : un package sur npm, un site de documentation, une identité propre, un pipeline de release, et une place dans Wonder Wagon, la famille d'outils que je construis.

Ce n'est pas un changelog. C'est ce qu'il a fallu pour faire passer un petit outil de "ça marche sur ma machine" à "un inconnu peut l'installer", et la poignée de décisions que je reprendrais.

## Le produit en une phrase

Le slogan a changé tard. La version précédente se terminait par "…Vous ne le retrouvez pas." Exact, et un peu sombre. Celui que j'ai validé est celui-ci :

**You already wrote it down. Find the passage that answers.** Vous l'avez déjà écrit. Trouvez le passage qui répond.

Le mot important, c'est *passage*.

Lorekeeper est une CLI à trois commandes. `lore init` crée un cerveau, qui n'est qu'un répertoire de Markdown, ou adopte un coffre que vous avez déjà sans réécrire un seul fichier. `lore capture` range une idée ou une URL. `lore search` classe les passages de ce cerveau par rapport à une question.

L'essayer tient en une ligne :

```sh
npx create-lorekeeper@0.1.0 init ~/brain
```

Vous obtenez cinq dossiers (`inbox/`, `daily/`, `notes/`, `sources/`, `entities/`), sept fichiers de départ, un `AGENTS.md` qui indique à un agent de code que le répertoire est interrogeable, et un manifeste dans `.lorekeeper/manifest.json` qui enregistre les fichiers écrits par l'outil. Tout le reste du répertoire vous appartient, et `lore` n'y touche pas.

Il fonctionne hors ligne. Pas de compte, pas de clé d'API, pas d'appel réseau, pas de modèle de langage. Il faut Node 24 ou plus, sur macOS ou Linux. Windows est hors du périmètre de la v0.1, et la CI le dit dans un commentaire à côté de la matrice.

## Décision 1 : l'unité, c'est le passage, pas le fichier

J'ai déjà écrit un article entier sur [pourquoi Lorekeeper récupère des fragments](/writing/lorekeeper-retrieves-spans), alors voici la version courte.

Une note de trois mille mots sur les déploiements n'est pas un fait. C'en est quarante. Si la recherche renvoie le fichier, vous obtenez la réponse plus trente-neuf choses qui lui disputent l'attention. C'est gênant pour moi quand je lis, et pire pour un agent qui paie chaque octet de contexte.

Chaque résultat est donc une adresse : un chemin, le titre sous lequel il se trouve, une plage de lignes, un score et le texte. Voici une exécution réelle sur une petite note écrite pour cet article, en posant la même question de deux façons dans un seul appel :

```sh
$ npx create-lorekeeper@0.1.0 search ~/brain \
    "retry policy" "what happens when the upload fails" --limit 2
notes/deploy-retries.md#When the upload fails:12-13  score 0.0164
~/brain/notes/deploy-retries.md
    The FTP step retries three times with a thirty-second backoff, then gives up.
    If it gives up, re-run the workflow; it only uploads changed files.

notes/README.md#notes:3-8  score 0.0161
~/brain/notes/README.md
    What you have worked out, written in your own words.
    ...
```

Deux lignes d'un fichier, pas le fichier. La note ne dit jamais "retry policy". C'est la deuxième formulation qui l'a trouvée, et la fusion l'a placée en tête.

Regardez aussi le deuxième résultat, parce que c'est la partie honnête.

## Pourquoi j'ai refusé de simuler la certitude

Ce deuxième résultat, c'est le README du dossier `notes/`. Il n'a rien à voir avec les nouvelles tentatives. Il obtient 0,0161 contre 0,0164 pour la bonne réponse.

Ces chiffres ne sont pas une confiance. Avec plusieurs formulations, Lorekeeper fusionne des listes classées par Reciprocal Rank Fusion, et 0,0164 vaut 1/61 : le score fusionné d'une première place. Il dit où un passage s'est classé, pas s'il est juste.

C'est la partie de la recherche où il est facile de mentir. **Un score de classement ne peut pas prouver qu'une chose est absente.** Pendant l'évaluation, une question témoin sans réponse nulle part dans le corpus s'est classée au-dessus de vraies questions qui en avaient une. Le premier résultat peut simplement être le meilleur d'un mauvais lot.

Lorekeeper n'a donc aucun seuil de pertinence. Nulle part. Un seuil aurait l'air responsable, et il transformerait un échec honnête en un "rien trouvé" plein d'assurance. À la place, le `AGENTS.md` qu'il écrit dit à l'agent de traiter les résultats comme des indices, de chercher à nouveau avec d'autres mots si les indices ne tranchent pas, et de dire "les éléments sont insuffisants" plutôt que "vos notes n'en parlent pas".

La recherche elle-même est un classement lexical déterministe. L'intelligence, c'est l'agent que vous utilisiez déjà. Je préfère livrer un outil exactement aussi malin qu'il l'est plutôt qu'un outil qui a l'air plus malin.

## Lui donner un visage

Lorekeeper est l'un des quatre outils d'une famille que j'appelle Wonder Wagon, avec Pathfinder, Forge et Lama. `lore --help` résume la relation en une ligne : "Pathfinder finds the way; Lorekeeper remembers the journey." Dans le brief de la famille, l'interface de Lorekeeper est une salle de lecture, volontairement la plus calme des quatre.

La marque est une étoile à quatre branches tenue dans un anneau : ce qui a été trouvé, et ce qui le garde. L'étincelle à quatre branches est le cliché actuel de l'IA, alors elle ne flotte jamais seule. Elle est toujours enclose. Pas de cerveau, pas de graphe de nœuds, pas de halo.

Certaines choses n'ont pas survécu au contact du réel. Une première étoile à côtés droits devenait une croix à 16 pixels, alors les flancs ont été courbés. Un laiton qui mesurait 2,70:1 contre son fond a été changé, pas livré avec une note de bas de page. La revue a repéré que le logotype était rogné par sa propre viewBox, environ deux unités de la jambe du R final coupées net, avant qu'aucun favicon n'en soit tiré.

![Le site de documentation de Lorekeeper en mode jour, avec le titre "You already wrote it down. Find the passage that answers."](/writing/building-and-launching-lorekeeper/home-day.png)

Le jour et la nuit ont chacun leur palette, et les deux sont mesurées. Le README embarque un en-tête de jour et un de nuit dans un `<picture>`, si bien que le mode sombre de GitHub reçoit celui de nuit et npm se rabat sur celui de jour. Dans un terminal couleur, `lore --help` peint le mot `Lorekeeper` en pervenche `#99A2F0` et se termine par un numéro de série atténué, `LK-047`. Pathfinder est `PF-047`, Forge est `FG-047`. La sortie redirigée, `NO_COLOR`, `TERM=dumb` et `--json` ne contiennent aucun code d'échappement.

![La même page, la nuit.](/writing/building-and-launching-lorekeeper/home-night.png)

Je n'ai pas utilisé la couleur de signal par défaut de l'adaptateur terminal, un doré `#E2B45C`. En 16 couleurs, elle retombe sur le jaune, qui est la sévérité `warn` de la famille et le plancher de Forge. La pervenche retombe sur un bleu vif, qui ne signifie rien d'autre. C'est le genre de décision qui n'apparaît que quand on teste aussi les terminaux ingrats.

## Décision 2 : la cohérence de marque comme un test qui échoue

Voici un problème que je n'attendais pas d'un exercice de marque. Les couleurs vivent dans deux dépôts.

Le `brand/tokens/tokens.json` de Lorekeeper est la source. La bibliothèque d'UI de Wonder Wagon a son propre thème `lorekeeper` qui reprend neuf de ces valeurs, entre jour et nuit. Quand j'ai promu ce thème de `draft` à `pilot`, l'accent de nuit est passé de `#5D64C3` à `#99A2F0` avec une encre sombre `#141521`, à 7,58:1.

Les valeurs copiées dérivent. Les deux côtés vérifient donc la même table de neuf valeurs.

Côté Lorekeeper, `brand/terminal/build.mjs --check` ne comparait qu'une seule valeur, `link`. Il compare maintenant les neuf. Côté Wonder Wagon, `proof/lorekeeper.ts` vérifie les mêmes neuf contre une fixture Lorekeeper épinglée, avec un test conçu pour échouer en cas de dérive. Lancée contre l'ancien pin de Wonder Wagon, la vérification élargie de Lorekeeper échoue sur `accent.night` et `accentInk.night`. À juste titre. C'était la promotion qui apparaissait comme un build rouge jusqu'au déplacement du pin.

Le site de documentation a le même problème, avec une variante. Vercel n'a pas de copie voisine de la bibliothèque d'UI, donc le thème arrive sous forme de fichier généré, et `theme:check` échoue s'il est périmé.

Entre tout cela, le contraste mesuré (`brand:check`, 52 paires) et les vérifications octet par octet des images du README et de l'enregistrement du terminal, "respecter la marque" a cessé d'être une opinion émise en revue. C'est une étape de CI.

## Décision 3 : un package public, un cœur privé

Le monorepo contient deux packages. `@lorekeeper/core` fait le vrai travail et reste privé. La CLI l'importe par son nom.

Cet import ne survit pas à la publication. Si la CLI publiée contient `import ... from '@lorekeeper/core'`, npm cherche un package qui n'existe pas et l'installation meurt sur un 404 avant que `lore` n'affiche son aide.

J'aurais pu publier le cœur comme second package public. J'avais décidé tôt que le cœur resterait privé, et je voulais que cette décision tienne. Le build prend donc exactement la sortie de `tsc` que les tests ont vue et y intègre le cœur dans un seul fichier, `dist/lore.js`, avec esbuild. Puis il vérifie sa propre sortie. Le bundle ne peut importer que des modules `node:*` et `yaml`, l'unique dépendance d'exécution, et le cœur doit réellement s'y trouver. L'un ou l'autre échec arrête le build.

Une vérification du package tourne sur chaque PR. Elle empaquette le tarball, l'inspecte, l'installe dans un préfixe vierge et lance le `lore` installé avec `--version`, `--help`, `init` et `search --json`. Seize vérifications. Le résultat est `create-lorekeeper-0.1.0.tgz` : quatre fichiers, 20 402 octets compressés.

Le build est déterministe, donc le tarball a une empreinte. Le sha1 enregistré quand j'ai validé l'empaquetage, `3ef401e3…`, est celui que le registre sert aujourd'hui.

À propos du nom. `lorekeeper` sur npm appartient à un projet sans rapport, donc le package s'appelle `create-lorekeeper` et la commande qu'il installe est `lore`. Pas idéal. Ça rend aussi `npx create-lorekeeper` naturel à lire, et je prends.

## Décision 4 : les preuves d'une release décrivent ce qui s'est passé

C'est celle qui me tient le plus à cœur, et elle concerne surtout du texte.

Avant la release, le README disait que Lorekeeper n'était sur aucun registre et s'installait depuis les sources. C'était vrai. Ça allait devenir faux le jour de la release, et la tentation est de "corriger" en avance pour que tout ait l'air prêt. Je ne l'ai pas fait. La PR qui a construit le README a laissé cette ligne volontairement en attente, avec une capture du terminal qui affichait encore `Lorekeeper 0.0.0`. Les deux ont changé dans la PR de release elle-même, celle qui fixait la version, avec la capture réenregistrée depuis le binaire empaqueté. Le site de documentation, là où les gens arrivent vraiment, a attendu plus longtemps. Sa PR a été fusionnée une fois le package sur le registre, et sa description s'ouvre sur une section intitulée "Publication is proven".

Le site de documentation applique la même idée de façon mécanique. Chaque sortie de commande qu'il affiche, y compris `lore --help` et `--version`, est générée depuis le binaire construit au moment du build. Et un build Vercel refuse de déployer si ce binaire annonce `0.0.0`. Le site ne peut pas revendiquer une release que le binaire n'a pas.

![La page de référence de la CLI en production, avec la vraie sortie de lore --help qui affiche Lorekeeper 0.1.0.](/writing/building-and-launching-lorekeeper/cli-night.png)

Le processus de release suit la même règle. La version vient d'un seul endroit, le titre le plus récent de `CHANGELOG.md`. Le manifeste, le tag Git et la GitHub Release doivent concorder avec lui, sinon le workflow refuse de tourner.

npm ne peut lier un trusted publisher qu'à un package qui existe déjà, donc `0.1.0` a été publié une fois à la main, depuis le tarball vérifié. Les releases suivantes passent par `release.yml`, conçu pour publier via le trusted publishing de npm avec provenance, relire la version depuis le registre, et seulement ensuite pousser le tag et créer la Release. Chaque étape saute un effet qui existe déjà, donc une exécution ratée est relancée, jamais "réparée" avec un nouveau numéro de version.

Ce design a été mis à l'épreuve plus tôt que prévu.

Le premier lancement de la release a échoué. Le workflow installe `npm@latest`, qui était npm 12.1.0, et npm 12 affiche `npm pack --json` sous forme d'objet indexé par nom de package au lieu d'un tableau. Mon script de vérification attendait le tableau. Cette exécution n'a rien publié, tagué ni créé, parce que les vérifications passent d'abord. Le correctif a appris les deux formes au script. Sous npm 12, le sha1 du tarball était identique octet pour octet à celui déjà sur le registre, ce qui est exactement ce qu'on veut savoir avant de taguer.

Relancée, l'exécution a vu `create-lorekeeper@0.1.0 is already on the registry; publish will be skipped`, a confirmé que le registre le servait, a tagué `v0.1.0` et créé la Release.

Pour mémoire, la CI exécute chaque pull request sur macOS et sur Linux.

## Le site

La documentation est sur [lorekeeper-bay.vercel.app](https://lorekeeper-bay.vercel.app). C'est de l'Astro statique, tout simplement. Pas de thème de documentation, pas de React. Douze pages de contenu dans une seule colonne de lecture avec un index sobre à côté, ce que "salle de lecture" a fini par vouloir dire en pratique.

Il fonctionne aussi hors ligne. Un service worker, généré à partir de la liste des pages du site, enregistre chaque page et ses ressources à la première visite. Ensuite, les pages s'ouvrent sans connexion. En ligne, il passe d'abord par le réseau, donc on ne lit jamais une page périmée quand on est connecté. Il ne demande rien d'autre que les fichiers du site. Un site de documentation pour un outil hors ligne qui cesse de marcher dans un avion m'aurait semblé une petite trahison.

## Ce que j'ai appris

Faire classer le bon passage par `lore search`, c'était la partie que je pensais difficile. La plupart des pull requests suivantes portaient sur autre chose : rendre vraie chaque affirmation publique sur l'outil. La couleur du README, la version sur l'écran d'aide, la ligne d'installation sur le site, le tag sur le commit.

Ce qui a marché, c'est de transformer chacune de ces affirmations en quelque chose qu'une machine vérifie. Les paires de contraste sont mesurées. Les valeurs du thème sont comparées entre dépôts. Les exemples de la documentation sont générés depuis le binaire. Le tarball a une empreinte. Le texte de la release attend le registre.

Rien de tout cela n'est glamour. Mais quand la release a cassé à cause de la forme d'un JSON auquel je n'avais jamais touché, rien n'a été livré à moitié. Elle s'est juste arrêtée, et m'a dit pourquoi.

Lorekeeper fait une petite chose : il retrouve le passage que vous avez déjà écrit. L'amener de l'idée à l'identité puis à un package qu'un inconnu peut installer m'a appris plus que le classement, et je garde les vérifications pour le prochain outil.

```sh
npx create-lorekeeper@0.1.0 init ~/brain
```

Le code est sur [GitHub](https://github.com/rikilamadrid/lorekeeper). S'il retrouve quelque chose que vous aviez oublié avoir écrit, j'aimerais le savoir.
