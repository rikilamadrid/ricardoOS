<!-- locale:en -->

Pathfinder 4.4.0 shipped on 18 September with a second execution mode. `human-in-the-loop` keeps direct control of one ticket session. `orchestrator` coordinates several dependency-safe workers at once, each in its own Git worktree, with human gates and integration as a separate decision.

The part worth explaining is the routing layer that sits between eligibility and dispatch. It estimates every ticket it is about to run, records that estimate in a closed schema, and then hands it to a policy that reads none of it.

That is not an oversight. It is the shape I wanted to ship first.

## A worker is a worktree

A claimed ticket gets one linked worktree at `.pathfinder/worktrees/<key>` on one branch `ticket/<key>-<slug>`. The worktree path is the worker's identity and the claim, and its own `context/current-ticket.md` is that worker's transient state, so two workers never share one.

What stops two workers owning the same ticket is a Git ref. A claim first creates `refs/pathfinder/claims/<key>`, which Git creates only if it does not already exist, under its own ref lock. Of any number of concurrent claims, exactly one proceeds. A claim that then fails removes the branch and the ref it created.

The engine holds no state of its own: every call re-derives its answer from Git, the worktrees and the ticket store.

## Three steps, and the boundaries are the point

```text
estimate(ticket, in-flight claims)  ->  execution profile
select(profile, routing policy)     ->  role, model, effort
dispatch(brief)                     ->  worker session
```

Those boundaries are where a later routing Feature plugs in. The module that assembles them knows the order of the steps and nothing about any policy.

## What the estimator counts

The profile is a closed schema, `pathfinder.execution-profile/1`:

```yaml
estimate:
  complexity:
    value: medium
    source: derived
    reason: "5 bullets under ## Changes"
  context:
    value: small
    source: derived
    reason: "3 paths named under ## Context"
  parallel-safety:
    value: isolated
    source: derived
    reason: "no other ticket is in flight"
  risk:
    value: unassessed
    source: derived
    reason: "no risk rule applies"
selection:
  policy: static
  role: developer
  model: inherited
  effort: inherited
```

Closed means an unknown field, an unknown value, a missing field or another schema version is refused. A different shape is `/2`, never an edit to `/1`.

Every derived field is a count over the ticket's own body, so the same ticket and the same board give the same bytes. Complexity counts top-level list items under the ticket's Changes heading: three or fewer is `low`, seven or fewer is `medium`, more is `high`. Context counts distinct backticked paths under the Context heading: three or fewer is `small`, eight or fewer is `medium`, more is `large`.

What counts as a path is defined rather than guessed, and that definition is most of the work. It is a backticked token with a slash whose first segment carries no dot, unless it is a dot-directory, or a token ending in a file extension. Versions and ticket keys like `53.2` are not paths. Braces expand, so `src/{a,b}.mjs` is two. A glob is cut back to its literal directory, so `packages/*/test/` is `packages`, and `**/*.md` names nothing.

The profile is orchestration state, not ticket content. Claiming writes it into the worker's own current-ticket file, and the ticket body never carries it.

## Parallel safety is the field that earns its keep

It is computed against every registered claim other than this ticket's whose ticket is not complete:

```text
serialize        names a file another in-flight ticket also names
shared-surface   names a directory containing, contained by, or equal to one another names
isolated         no overlap, nothing in flight, or no declared relevant area
```

Tickets the same plan selected earlier in the round count as in flight, because two tickets dispatched together run together.

Risk is derived by exactly two rules. `low` is complexity `low` with context `small` and `isolated`. `high` is complexity `high` with context `large`. Everything else is `unassessed`, and the engine does not guess a middle. I can assess risk myself with a reason, and the profile then marks that value `assessed` and keeps the reason. No other field can be assessed, and the orchestrator never picks a model.

## The policy socket, and why static ships alone

A routing policy is one module exporting a synchronous `select(estimate, session)`, where the session is `implementation` or `review`. The registry finds policies by file name. A project names one on an optional second marker line in its execution-mode file, and no marker means `static`. A name the engine does not ship refuses the claim and lists the ones it has.

Two details make the socket worth having. A policy receives a deep-frozen copy of the estimate, so a write to it is refused and cannot alter what the profile records. And no scheduler, claim, status or brief code names a policy at all, with a test that proves it by adding one.

Version one ships `static` alone, and this is the whole of it:

```js
export function select(profile, { session }) {
  return {
    role: session === "review" ? "tester" : "developer",
    model: "inherited",
    effort: "inherited",
  };
}
```

`inherited` means whatever the session dispatching the worker already runs on. It reads nothing from the estimate.

So the estimator computes thresholds that the shipped policy ignores. They are coarse on purpose. Their job in this version is to be a stable, inspectable input that a later policy can be written against, and to sit visibly in every profile so I can judge whether they were any good. Nothing has tuned them against outcomes yet, and I am not going to let a number I never validated start choosing models.

The boring policy is also the reproducible one. A run is reviewable because the selection depends on nothing but the session type.

## It survived its workers dying

During the acceptance run, Pathfinder dispatched two workers concurrently while a third stayed correctly blocked. Both live Codex sessions hit usage limits and ended, their claims went stale with uncommitted work preserved, and replacement sessions resumed the same branches, worktrees and profiles. Any claim the current run did not start is stale until resumed deliberately, and a stale claim is never dispatched twice.

The limits, as the acceptance record states them: the live workers never hit a human gate or a file conflict, and nothing in this release measures concurrent against serial delivery. So nothing here claims it is faster.

## What it does not do

No dynamic model routing. No daemon, broker, queue, database or server. No automatic merge, no bypassed review, no unlimited agents. A ticket whose status the engine cannot read is never eligible and never unblocks a dependent.

The next policy has somewhere to go, which was the point of shipping the socket without it.

Pathfinder 4.4.0 salió el 18 de septiembre con un segundo modo de ejecución. `human-in-the-loop` mantiene el control directo de una sesión de ticket. `orchestrator` coordina varios workers seguros en dependencias a la vez, cada uno en su propio worktree de Git, con gates humanos e integración como decisión aparte.

Lo que merece explicación es la capa de enrutado que se sitúa entre la elegibilidad y el despacho. Estima cada ticket que va a ejecutar, registra esa estimación en un esquema cerrado, y después se la entrega a una política que no lee nada de ella.

No es un descuido. Es la forma que quería publicar primero.

## Un worker es un worktree

Un ticket reclamado recibe un worktree enlazado en `.pathfinder/worktrees/<key>` sobre una rama `ticket/<key>-<slug>`. La ruta del worktree es la identidad del worker y el claim, y su propio `context/current-ticket.md` es el estado transitorio de ese worker, así que dos workers nunca comparten uno.

Lo que impide que dos workers sean dueños del mismo ticket es una referencia de Git. Un claim crea primero `refs/pathfinder/claims/<key>`, que Git solo crea si no existe ya, bajo su propio bloqueo de referencias. De cualquier número de claims concurrentes, exactamente uno prospera. Un claim que luego falla elimina la rama y la referencia que había creado.

El motor no guarda estado propio: cada llamada vuelve a derivar su respuesta de Git, los worktrees y el almacén de tickets.

## Tres pasos, y las fronteras son lo importante

```text
estimate(ticket, claims en vuelo)  ->  perfil de ejecución
select(perfil, política de enrutado) ->  rol, modelo, esfuerzo
dispatch(brief)                    ->  sesión de worker
```

Esas fronteras son donde se enchufa una Feature de enrutado posterior. El módulo que las ensambla conoce el orden de los pasos y nada sobre ninguna política.

## Qué cuenta el estimador

El perfil es un esquema cerrado, `pathfinder.execution-profile/1`:

```yaml
estimate:
  complexity:
    value: medium
    source: derived
    reason: "5 bullets under ## Changes"
  context:
    value: small
    source: derived
    reason: "3 paths named under ## Context"
  parallel-safety:
    value: isolated
    source: derived
    reason: "no other ticket is in flight"
  risk:
    value: unassessed
    source: derived
    reason: "no risk rule applies"
selection:
  policy: static
  role: developer
  model: inherited
  effort: inherited
```

Cerrado significa que un campo desconocido, un valor desconocido, un campo ausente u otra versión del esquema se rechazan. Una forma distinta es `/2`, nunca una edición de `/1`.

Cada campo derivado es un recuento sobre el propio cuerpo del ticket, así que el mismo ticket y el mismo tablero dan los mismos bytes. La complejidad cuenta los elementos de lista de primer nivel bajo el encabezado de cambios del ticket: tres o menos es `low`, siete o menos es `medium`, más es `high`. El contexto cuenta rutas distintas entre comillas invertidas bajo el encabezado de contexto: tres o menos es `small`, ocho o menos es `medium`, más es `large`.

Qué cuenta como ruta está definido y no adivinado, y esa definición es la mayor parte del trabajo. Es un token entre comillas invertidas con una barra cuyo primer segmento no lleva punto, salvo que sea un directorio con punto, o un token que termina en una extensión de fichero. Versiones y claves de ticket como `53.2` no son rutas. Las llaves se expanden, así que `src/{a,b}.mjs` son dos. Un glob se recorta a su directorio literal, así que `packages/*/test/` es `packages`, y `**/*.md` no nombra nada.

El perfil es estado de orquestación, no contenido del ticket. Reclamar lo escribe en el fichero de ticket actual del propio worker, y el cuerpo del ticket nunca lo lleva.

## La seguridad en paralelo es el campo que se gana el sueldo

Se calcula contra cada claim registrado distinto del de este ticket cuyo ticket no esté completo:

```text
serialize        nombra un fichero que otro ticket en vuelo también nombra
shared-surface   nombra un directorio que contiene, está contenido en, o es igual a uno que otro nombra
isolated         sin solape, nada en vuelo, o sin área relevante declarada
```

Los tickets que el mismo plan seleccionó antes en la ronda cuentan como en vuelo, porque dos tickets despachados juntos se ejecutan juntos.

El riesgo se deriva con exactamente dos reglas. `low` es complejidad `low` con contexto `small` y `isolated`. `high` es complejidad `high` con contexto `large`. Todo lo demás es `unassessed`, y el motor no adivina un punto medio. Yo puedo evaluar el riesgo a mano con una razón, y entonces el perfil marca ese valor como `assessed` y conserva la razón. Ningún otro campo se puede evaluar así, y el orquestador nunca elige un modelo.

## El zócalo de políticas, y por qué solo se publica static

Una política de enrutado es un módulo que exporta un `select(estimate, session)` síncrono, donde la sesión es `implementation` o `review`. El registro encuentra las políticas por nombre de fichero. Un proyecto nombra la suya en una segunda línea marcadora opcional de su fichero de modo de ejecución, y sin marcador la política es `static`. Un nombre que el motor no publica rechaza el claim y lista los que sí tiene.

Dos detalles hacen que el zócalo valga la pena. Una política recibe una copia profundamente congelada de la estimación, así que una escritura sobre ella se rechaza y no puede alterar lo que el perfil registra. Y ningún código de planificador, claim, estado o brief nombra política alguna, con un test que lo demuestra añadiendo una.

La versión uno publica `static` en solitario, y esto es todo lo que hay:

```js
export function select(profile, { session }) {
  return {
    role: session === "review" ? "tester" : "developer",
    model: "inherited",
    effort: "inherited",
  };
}
```

`inherited` significa aquello sobre lo que ya corre la sesión que despacha al worker. No lee nada de la estimación.

Así que el estimador calcula umbrales que la política publicada ignora. Son groseros a propósito. Su trabajo en esta versión es ser una entrada estable e inspeccionable contra la que escribir una política posterior, y quedar a la vista en cada perfil para que yo pueda juzgar si eran buenos. Nada los ha ajustado todavía contra resultados reales, y no voy a dejar que un número que nunca validé empiece a elegir modelos.

La política aburrida es además la reproducible. Una ejecución es revisable porque la selección no depende de nada salvo del tipo de sesión.

## Sobrevivió a la muerte de sus workers

Durante la ejecución de aceptación, Pathfinder despachó dos workers concurrentes mientras un tercero seguía correctamente bloqueado. Las dos sesiones Codex en vivo alcanzaron sus límites de uso y terminaron, sus claims quedaron obsoletos con el trabajo sin commitear preservado, y sesiones de reemplazo reanudaron las mismas ramas, worktrees y perfiles. Cualquier claim que la ejecución actual no haya iniciado está obsoleto hasta que se reanude deliberadamente, y un claim obsoleto nunca se despacha dos veces.

Los límites, tal como los enuncia el registro de aceptación: los workers en vivo nunca llegaron a un gate humano ni a un conflicto de ficheros, y nada en esta release mide la entrega concurrente frente a la serial. Así que nada aquí afirma que sea más rápida.

## Lo que no hace

Nada de enrutado dinámico de modelos. Ni demonio, ni broker, ni cola, ni base de datos, ni servidor. Ni merge automático, ni revisión saltada, ni agentes ilimitados. Un ticket cuyo estado el motor no puede leer nunca es elegible y nunca desbloquea a un dependiente.

La siguiente política tiene a dónde ir, que era el objetivo de publicar el zócalo sin ella.

Ce qui mérite une explication, c'est la couche de routage placée entre l'éligibilité et l'envoi. Elle estime chaque ticket qu'elle va lancer, consigne cette estimation dans un schéma fermé, puis la confie à une politique qui n'en lit rien.

Ce n'est pas un oubli. C'est la forme que je voulais livrer en premier.

Sur un nombre quelconque de claims concurrents, exactement un aboutit. Un claim qui échoue ensuite supprime la branche et la référence qu'il avait créées.

Le moteur ne conserve aucun état propre : chaque appel redérive sa réponse depuis Git, les worktrees et le magasin de tickets.

```text

```

Ces frontières sont l'endroit où une future Feature de routage vient se brancher. Le module qui les assemble connaît l'ordre des étapes et rien d'aucune politique.

## Ce que compte l'estimateur


Le profil est un état d'orchestration, pas un contenu de ticket. Le claim l'écrit dans le fichier de ticket courant propre au worker, et le corps du ticket ne le porte jamais.

## La sûreté en parallèle est le champ qui justifie sa place

Elle est calculée contre chaque claim enregistré autre que celui de ce ticket, dont le ticket n'est pas terminé :

```text
serialize        nomme un fichier qu'un autre ticket en vol nomme aussi
shared-surface   nomme un répertoire contenant, contenu dans, ou égal à un autre nommé ailleurs
isolated         aucun recouvrement, rien en vol, ou aucune zone pertinente déclarée
```

Le risque est dérivé par exactement deux règles. `low` correspond à une complexité `low` avec un contexte `small` et `isolated`. `high` correspond à une complexité `high` avec un contexte `large`. Tout le reste est `unassessed`, et le moteur ne devine pas de milieu. Je peux évaluer le risque moi-même avec une justification, et le profil marque alors cette valeur `assessed` et conserve la raison. Aucun autre champ ne peut être évalué ainsi, et l'orchestrateur ne choisit jamais un modèle.

## L'emplacement pour les politiques, et pourquoi static est seul livré

Une politique de routage est un module exportant un `select(estimate, session)` synchrone, où la session vaut `implementation` ou `review`. Le registre trouve les politiques par nom de fichier. Un projet nomme la sienne sur une seconde ligne de marqueur optionnelle dans son fichier de mode d'exécution, et sans marqueur la politique est `static`. Un nom que le moteur ne livre pas refuse le claim et liste ceux dont il dispose.

Deux détails rendent cet emplacement utile. Une politique reçoit une copie profondément gelée de l'estimation, donc une écriture dessus est refusée et ne peut pas altérer ce que le profil consigne. Et aucun code d'ordonnanceur, de claim, d'état ou de brief ne nomme la moindre politique, avec un test qui le prouve en en ajoutant une.

La version un livre `static` seul, et le voici en entier :

```js
export function select(profile, { session }) {
  return {
    role: session === "review" ? "tester" : "developer",
    model: "inherited",
    effort: "inherited",
  };
}
```

`inherited` signifie ce sur quoi tourne déjà la session qui envoie le worker. Elle ne lit rien de l'estimation.

L'estimateur calcule donc des seuils que la politique livrée ignore. Ils sont grossiers à dessein. Leur travail dans cette version est d'être une entrée stable et inspectable contre laquelle écrire une politique ultérieure, et de rester visibles dans chaque profil pour que je puisse juger s'ils valaient quelque chose. Rien ne les a encore ajustés face à des résultats réels, et je ne vais pas laisser un nombre que je n'ai jamais validé se mettre à choisir des modèles.

La politique ennuyeuse est aussi la reproductible. Une exécution est relisable parce que la sélection ne dépend de rien d'autre que du type de session.

## Il a survécu à la mort de ses workers

Pendant le run d'acceptation, Pathfinder a envoyé deux workers en parallèle tandis qu'un troisième restait correctement bloqué. Les deux sessions Codex en direct ont atteint leurs limites d'usage et se sont arrêtées, leurs claims sont passés en obsolète avec le travail non commité préservé, et des sessions de remplacement ont repris les mêmes branches, worktrees et profils. Tout claim que le run courant n'a pas démarré lui-même est obsolète jusqu'à une reprise délibérée, et un claim obsolète n'est jamais envoyé deux fois.

Les limites, telles que le registre d'acceptation les énonce : les workers en direct n'ont jamais atteint de gate humain ni de conflit de fichiers, et rien dans cette version ne mesure la livraison concurrente face à la livraison en série. Donc rien ici ne prétend qu'elle est plus rapide.

## Ce qu'il ne fait pas

Pas de routage dynamique de modèles. Pas de démon, de broker, de file, de base de données ni de serveur. Pas de merge automatique, pas de revue contournée, pas d'agents illimités. Un ticket dont le moteur ne sait pas lire l'état n'est jamais éligible et ne débloque jamais un dépendant.

La prochaine politique a où aller, ce qui était tout l'intérêt de livrer l'emplacement sans elle.
