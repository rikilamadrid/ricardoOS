Pathfinder is the workflow kit I use to build software with coding agents. In orchestrator mode each ticket goes through a Developer, an Adversary that tries to break the work, and an independent Tester, then stops at a gate where I decide what gets merged. ([More on that here](/writing/pathfinder-4-4-0).)

Most of that loop is procedure: which role runs next, whether a report matches the current PR head, whether a claim is done. Code answers those, because they have right answers.

Two places kept asking a different question. Not "what state are we in?" but "what does this evidence mean?" That's where I've started using a model. Not as an orchestrator. As a reader.

```text
model = epistemic authority
code  = procedural authority
```

The model says what it thinks the evidence means. Code decides what that allows. I decide whether it happens.

## A second reader for the evidence

Feature 56 adds an optional Evidence Judge. After the Tester passes a ticket and before it reaches me, Pathfinder can ask Jev, TypeSafe's structured-decision model, one question per verification item: does the recorded evidence support this criterion?

Jev answers with typed choices and confidences, not prose. I can validate a choice from a closed set. I can't validate an essay.

The judge can't PASS or FAIL a ticket, accept work, merge, dispatch an agent or change lifecycle state. Any failure, timeout or malformed answer escalates to me. It's off by default, and an API key in the environment never turns it on.

The hard part was deciding what to send. My first attempt sent the recorded evidence through a secret detector. It went through eight adversarial rounds, and they kept finding syntax it missed. So the boundary became a projection instead of a filter.

Beside their raw evidence, the Tester and Adversary each write a one-line summary in restricted "judge prose": at most 280 characters, only letters, digits, spaces and basic punctuation. Without colons, equals signs, slashes, quotes or newlines, credential pairs, key-value assignments, URLs, headers, JSON and log dumps can't be written at all. "The expired token was rejected with HTTP 401." passes. A curl command doesn't.

Raw commands, logs, file paths, the PR URL and the head SHA stay local. The provider only sees generated ids that map back to local records. The docs are explicit about the limit: this stops accidental leaks of technical payloads and common credentials. It isn't DLP against a short secret written as a normal sentence.

The transport has one rule: **validated bytes are transmitted bytes.** The provider declares its endpoint and headers up front, and the guarded fetch sends exactly the strings it checked. If you validate one object and serialize another, the check is decoration. Ticket 57.3 found a real case of that, where a serialization hook could swap content after validation, and fixed it by freezing a snapshot first.

## A concern that won't resolve

Feature 57 handles a messier moment. Review is complete, but a concern is still open, like "Repeated boundary input lacks an observation." Is that a missing test, an assumption to attack, or a requirement only I can clarify?

Jev can now be asked exactly that, with three possible answers:

- **Tester**: gather more evidence
- **Adversary**: run a new experiment
- **Human**: clarify or decide

There's no Developer route. Only confirmed Tester findings can authorize a repair. There's no continue, dispatch or merge answer either, and a response with any field outside the contract is rejected.

Deterministic policy then maps the validated answer. Tester or Adversary is recommended only when there's no flagged concern, the cited evidence resolves, and confidence is at least 0.8. Everything else goes to Human, including a confident answer that flags security, low confidence, a wrong model, a timeout or a provider failure. Uncertainty can only make the result more conservative.

```text
local workflow evidence      raw logs, commands, SHAs, credentials stay here
        ▼
bounded projection           restricted prose, generated ids
        ▼
guarded Jev transport        pinned model, one request, no retry
        ▼
strict validation            closed contract, refs must resolve
        ▼
deterministic policy         Tester | Adversary | Human
        ▼
human-authorized follow-up   separate command, separate authorization
```

Every arrow can refuse, and every refusal lands on Human.

## Why it's built in slices

- **57.1**: contract and policy, with no network at all. Every combination is table-tested; all 4,094 combined restriction cases resolve to Human.
- **57.2**: a routing-only projection, still offline, independent of the Evidence Judge and its credentials.
- **57.3**: the guarded transport, tested only against a local double.
- **57.4**: a budget of two attempts per ticket that I initialize explicitly. Failures count, nothing is refunded quietly, and nothing retries automatically.
- **57.5**: fixed a bug that predated routing. Asking for more investigation at the same commit left the old Tester PASS eligible, so work could go straight back to done. Follow-up now retires the old reports and requires fresh ones.
- **57.6**: the explicit entrypoint. It needs its own config and per-call consent, and rereads all state after the provider answers. If anything changed, the answer is rejected.

## Where it stands

Feature 56 and tickets 57.1 to 57.6 are merged. 57.7 (hostile and interrupted scenarios) is in progress, and 57.8 (docs and acceptance proof) hasn't started. Neither feature is in an npm release yet. No routing test has called Jev live, and the 0.8 thresholds are provisional, not calibrated accuracy.

The tradeoffs are real. Getting one recommendation takes a prepared request, a budget, consent, and then a separate human decision to act on it. That friction is on purpose: a recommendation should be cheap to make and hard to act on by accident. The model sees a thin slice, so some concerns will come back as "insufficient context" and go to me. And a short secret typed as plain prose can still get through.

## The point

The goal isn't more AI in the loop. Most of the loop shouldn't have a model in it at all. I use one only where the question is really about meaning, and where a confident wrong answer is cheap because it reaches me as a recommendation, not a state change.

Jev reads. Pathfinder decides what's allowed. I decide what happens.

## Un segundo lector para la evidencia

La Feature 56 añade un Evidence Judge opcional. Después de que el Tester aprueba un ticket y antes de que llegue a mí, Pathfinder puede preguntarle a Jev, el modelo de decisiones estructuradas de TypeSafe, una pregunta por cada ítem de verificación: ¿la evidencia registrada respalda este criterio?

Jev responde con opciones tipadas y niveles de confianza, no con prosa. Puedo validar una opción de un conjunto cerrado. No puedo validar un ensayo.

El juez no puede dar PASS o FAIL, aceptar trabajo, mergear, despachar un agente ni cambiar el estado del ciclo de vida. Cualquier fallo, timeout o respuesta malformada me escala a mí. Viene apagado por defecto, y una API key en el entorno nunca lo enciende.

Lo difícil fue decidir qué enviar. Mi primer intento pasaba la evidencia registrada por un detector de secretos. Pasó por ocho rondas adversariales, y seguían encontrando sintaxis que se le escapaba. Así que el límite pasó a ser una proyección en lugar de un filtro.

Junto a su evidencia cruda, el Tester y el Adversary escriben cada uno un resumen de una línea en "judge prose" restringida: como máximo 280 caracteres, solo letras, dígitos, espacios y puntuación básica. Sin dos puntos, signos igual, barras, comillas ni saltos de línea, los pares de credenciales, las asignaciones clave-valor, URLs, headers, JSON y volcados de logs directamente no se pueden escribir. "The expired token was rejected with HTTP 401." pasa. Un comando curl no.

Los comandos, logs, rutas de archivos, la URL del PR y el SHA del head se quedan en local. El proveedor solo ve ids generados que apuntan a registros locales. La documentación es explícita sobre el límite: esto evita filtraciones accidentales de payloads técnicos y credenciales comunes. No es DLP frente a un secreto corto escrito como una frase normal.

El transporte tiene una regla: **los bytes validados son los bytes transmitidos.** El proveedor declara su endpoint y sus headers de antemano, y el fetch protegido envía exactamente las cadenas que comprobó. Si validas un objeto y serializas otro, la validación es decoración. El ticket 57.3 encontró un caso real de eso, un hook de serialización que podía cambiar el contenido después de validarlo, y lo arregló congelando un snapshot primero.

## Una preocupación que no se resuelve

La Feature 57 cubre un momento más desordenado. La revisión está completa, pero sigue abierta una preocupación, como "Repeated boundary input lacks an observation." ¿Es un test que falta, una suposición que atacar o un requisito que solo yo puedo aclarar?

Ahora se le puede preguntar exactamente eso a Jev, con tres respuestas posibles:

- **Tester**: reunir más evidencia
- **Adversary**: ejecutar un experimento nuevo
- **Human**: aclarar o decidir

No existe una ruta Developer. Solo los hallazgos confirmados del Tester pueden autorizar una reparación. Tampoco hay respuestas de continuar, despachar ni mergear, y una respuesta con cualquier campo fuera del contrato se rechaza.

Después, una política determinista traduce la respuesta validada. Tester o Adversary solo se recomiendan cuando no hay ninguna preocupación señalada, la evidencia citada existe y la confianza es al menos 0.8. Todo lo demás va a Human, incluida una respuesta segura que señala seguridad, baja confianza, un modelo incorrecto, un timeout o un fallo del proveedor. La incertidumbre solo puede hacer el resultado más conservador.

```text
local workflow evidence      raw logs, commands, SHAs, credentials stay here
        ▼
bounded projection           restricted prose, generated ids
        ▼
guarded Jev transport        pinned model, one request, no retry
        ▼
strict validation            closed contract, refs must resolve
        ▼
deterministic policy         Tester | Adversary | Human
        ▼
human-authorized follow-up   separate command, separate authorization
```

Cada flecha puede rechazar, y cada rechazo termina en Human.

## Por qué se construye por partes

- **57.1**: contrato y política, sin red. Cada combinación se prueba con tablas; los 4.094 casos combinados de restricción terminan en Human.
- **57.2**: una proyección solo para routing, todavía sin red, independiente del Evidence Judge y de sus credenciales.
- **57.3**: el transporte protegido, probado solo contra un doble local.
- **57.4**: un presupuesto de dos intentos por ticket que inicializo yo de forma explícita. Los fallos cuentan, nada se devuelve en silencio y nada se reintenta solo.
- **57.5**: arregló un bug anterior al routing. Pedir más investigación en el mismo commit dejaba elegible el PASS viejo del Tester, así que el trabajo podía volver directo a done. Ahora el seguimiento retira los reportes viejos y exige otros nuevos.
- **57.6**: el punto de entrada explícito. Necesita su propia configuración y consentimiento por llamada, y vuelve a leer todo el estado cuando el proveedor responde. Si algo cambió, la respuesta se rechaza.

## Dónde está

La Feature 56 y los tickets 57.1 a 57.6 están mergeados. 57.7 (escenarios hostiles e interrumpidos) está en curso y 57.8 (documentación y prueba de aceptación) no ha empezado. Ninguna de las dos features está todavía en una versión de npm. Ningún test de routing ha llamado a Jev en vivo, y los umbrales de 0.8 son provisionales, no una precisión calibrada.

Los compromisos son reales. Conseguir una recomendación requiere una solicitud preparada, un presupuesto, consentimiento y luego una decisión humana aparte para actuar. Esa fricción es a propósito: una recomendación debería ser barata de producir y difícil de ejecutar por accidente. El modelo ve una porción estrecha, así que algunas preocupaciones volverán como "contexto insuficiente" y llegarán a mí. Y un secreto corto escrito como prosa normal todavía puede pasar.

## La idea

El objetivo no es meter más IA en el ciclo. La mayor parte del ciclo no debería tener un modelo. Solo lo uso donde la pregunta es de verdad sobre significado, y donde una respuesta equivocada pero segura sale barata porque me llega como recomendación, no como cambio de estado.

Jev lee. Pathfinder decide qué está permitido. Yo decido qué pasa.

La documentation est claire sur la limite : cela empêche les fuites accidentelles de payloads techniques et de credentials courantes. Ce n'est pas de la DLP face à un secret court écrit comme une phrase ordinaire.

Si on valide un objet puis qu'on en sérialise un autre, la validation est décorative. Le ticket 57.3 en a trouvé un cas réel, un hook de sérialisation qui pouvait remplacer le contenu après validation, et l'a corrigé en figeant d'abord un snapshot.

## Une préoccupation qui ne se résout pas

La Feature 57 traite un moment plus confus. La revue est complète, mais une préoccupation reste ouverte, comme « Repeated boundary input lacks an observation. » Est-ce un test manquant, une hypothèse à attaquer, ou une exigence que je suis le seul à pouvoir clarifier ?

On peut désormais poser exactement cette question à Jev, avec trois réponses possibles :

- **Tester** : rassembler plus de preuves
- **Adversary** : lancer une nouvelle expérience
- **Human** : clarifier ou décider

Il n'y a pas de route Developer. Seuls les findings confirmés du Tester peuvent autoriser une réparation. Il n'y a pas non plus de réponse continuer, lancer ou merger, et une réponse qui contient un champ hors contrat est rejetée.

Ensuite, une politique déterministe traduit la réponse validée. Tester ou Adversary ne sont recommandés que s'il n'y a aucune préoccupation signalée, que la preuve citée existe et que la confiance atteint au moins 0.8. Tout le reste va vers Human, y compris une réponse sûre d'elle qui signale un problème de sécurité, une confiance basse, un mauvais modèle, un timeout ou une panne du fournisseur. L'incertitude ne peut que rendre le résultat plus prudent.

```text
        ▼

```

## Pourquoi c'est construit par tranches

- **57.1** : contrat et politique, sans aucun réseau. Chaque combinaison est testée en table ; les 4 094 cas de restriction combinés aboutissent tous à Human.
- **57.2** : une projection propre au routing, toujours hors ligne, indépendante de l'Evidence Judge et de ses credentials.
- **57.3** : le transport protégé, testé uniquement contre un double local.
- **57.4** : un budget de deux tentatives par ticket, que j'initialise explicitement. Les échecs comptent, rien n'est remboursé en silence et rien n'est relancé automatiquement.
- **57.5** : a corrigé un bug antérieur au routing. Demander plus d'investigation sur le même commit laissait l'ancien PASS du Tester éligible, et le travail pouvait revenir directement à done. Le suivi retire maintenant les anciens rapports et en exige de nouveaux.
- **57.6** : le point d'entrée explicite. Il demande sa propre configuration et un consentement par appel, et relit tout l'état après la réponse du fournisseur. Si quelque chose a changé, la réponse est rejetée.

## Où on en est

La Feature 56 et les tickets 57.1 à 57.6 sont mergés. 57.7 (scénarios hostiles et interrompus) est en cours, et 57.8 (documentation et preuve d'acceptation) n'a pas commencé. Aucune des deux features n'est encore dans une version npm. Aucun test de routing n'a appelé Jev en conditions réelles, et les seuils de 0.8 sont provisoires, pas une précision calibrée.

Les compromis sont réels. Obtenir une recommandation demande une requête préparée, un budget, un consentement, puis une décision humaine séparée pour agir. Cette friction est voulue : une recommandation devrait coûter peu à produire et être difficile à appliquer par accident. Le modèle ne voit qu'une tranche fine, donc certaines préoccupations reviendront avec un « contexte insuffisant » et arriveront jusqu'à moi. Et un secret court tapé en prose ordinaire peut encore passer.

## L'idée

Le but n'est pas de mettre plus d'IA dans la boucle. La majeure partie de la boucle ne devrait pas contenir de modèle du tout. Je n'en utilise un que là où la question porte vraiment sur le sens, et où une mauvaise réponse assurée coûte peu parce qu'elle m'arrive comme une recommandation, pas comme un changement d'état.

Jev lit. Pathfinder décide de ce qui est permis. Je décide de ce qui se passe.
